# Требования otbor

Статус: живой документ. Дата: 02.11.2026.

Это не backlog и не ADR. Здесь фиксируем, **что** система должна делать и как
проверить, что это сделано. Порядок работ и технические решения живут в
отдельных документах.

## Формат

- ID: `REQ-<область>-<номер>`, например `REQ-BL-001`.
- Статус: `proposed` → `accepted` → `in-progress` → `done` | `dropped`.
- Приоритет: `must`, `should`, `may`.
- Формулировка: одно проверяемое утверждение.
- Критерии приёмки: что именно увидит или проверит оператор.
- Слова «ДОЛЖЕН / СЛЕДУЕТ / МОЖЕТ» — в смысле RFC 2119.
- Если требование меняет архитектуру, на него ссылается ADR в
  `docs/architecture/`.

## BL — чёрный список

### REQ-BL-001. Общий список приложения

- Статус: `proposed`
- Приоритет: `must`
- Компании и отдельные вакансии можно добавить в чёрный список на уровне
  приложения. Этот список ДОЛЖЕН действовать на все hh-аккаунты пользователя.
- Критерии приёмки:
  - запись видна в разделе «Чёрный список» с областью «Приложение»;
  - вакансия компании из списка не попадает в выдачу и в отклики ни по
    одному hh-аккаунту;
  - решение по такой вакансии содержит причину `blocked_blacklist` и слой
    `app`.

### REQ-BL-002. Список конкретного hh-аккаунта

- Статус: `proposed`
- Приоритет: `must`
- У каждого hh-аккаунта есть дополнительный чёрный список. Он ДОЛЖЕН
  складываться с общим списком приложения, а не заменять его.
- Критерии приёмки:
  - запись видна с областью «Аккаунт hh» и привязкой к аккаунту;
  - блокировка действует только для этого аккаунта;
  - причина решения указывает слой `hh_account` и id аккаунта.

### REQ-BL-003. Скрытые в самом hh

- Статус: `proposed`
- Приоритет: `should`
- Скрытые вакансии и работодатели из кабинета hh ДОЛЖНЫ импортироваться как
  третий, дополнительный слой блокировок. Источник записи —
  `hh_hidden`, а не ручной список.
- Критерии приёмки:
  - импорт не создаёт дублей с ручными записями;
  - запись помечена как «скрыто в hh»;
  - повторная синхронизация обновляет `last_seen_at`, а не плодит копии;
  - причина решения указывает слой `hh_native`.

### REQ-BL-004. Приоритет слоёв

- Статус: `proposed`
- Приоритет: `must`
- Итоговая блокировка — объединение трёх слоёв: приложение, hh-аккаунт,
  скрытое в hh. Ни один слой не отменяет другой. Если сработало несколько,
  решение ДОЛЖНО сохранить самый конкретный слой и перечислить остальные.
- Критерии приёмки:
  - вакансия блокируется, если совпала хотя бы с одним слоем;
  - в решении видно, какой слой сработал;
  - снятие записи из одного слоя не разблокирует вакансию, если её держит
    другой слой.

### REQ-BL-005. Что именно блокируется

- Статус: `proposed`
- Приоритет: `must`
- Поддерживаются два типа цели: работодатель и конкретная вакансия.
  Блокировка работодателя ДОЛЖНА скрывать все его вакансии, включая новые.
  Блокировка вакансии — только эту вакансию.
- Критерии приёмки:
  - можно добавить компанию по названию, id hh или ссылке;
  - можно добавить вакансию по id hh или ссылке;
  - новые вакансии заблокированной компании скрываются без ручных действий.

### REQ-BL-006. Корпус не удаляется

- Статус: `proposed`
- Приоритет: `must`
- Блокировка — это фильтр видимости и решений, а не удаление из корпуса.
  Вакансия остаётся в БД, чтобы работали история, поиск и разблокировка.
- Критерии приёмки:
  - после блокировки строка остаётся в `vacancy`;
  - в обычной выдаче её нет;
  - после снятия блокировки она снова видна без повторного обхода.

### REQ-BL-007. Управление и аудит

- Статус: `proposed`
- Приоритет: `should`
- В UI ДОЛЖНЫ быть вкладки «Приложение», «Аккаунт hh», «Скрыто в hh»,
  поиск, добавление, удаление и счётчики. У записи хранятся источник, причина,
  автор, время создания и последнего подтверждения.
- Критерии приёмки:
  - оператор видит, кто и когда добавил запись;
  - импортированные из hh записи нельзя перепутать с ручными;
  - удаление ручной записи не трогает импортированные.

## PRESET — пресеты

### REQ-PRESET-001. Пресет — это набор правил

- Статус: `in-progress`
- Приоритет: `must`
- Пресет ДОЛЖЕН фильтровать корпус по почти всем параметрам вакансии, а не
  по трём полям. Правила складываются через `AND`.
- Поддерживаемые поля: заголовок, описание, навыки, ключевые слова,
  работодатель, город, зарплата от/до, валюта, грейд, формат работы, опыт,
  тип занятости, свежесть, архив, вердикт заголовка, роль, источник, число
  отзывов, длина описания, число навыков.
- Критерии приёмки:
  - в UI можно добавить и удалить правило;
  - операторы ограничены типом поля;
  - сохранённый пресет возвращает то же число вакансий, что и предпросмотр.

### REQ-PRESET-002. Гейт — частный случай

- Статус: `in-progress`
- Приоритет: `must`
- Проверка заголовка ДОЛЖНА быть одним из правил пресета
  (`field = "gate"`), а не отдельной сущностью или обязательным шагом.
- Критерии приёмки:
  - правило `gate = match|unknown|reject` можно сочетать с любыми другими;
  - пресет без правила `gate` не фильтрует по вердикту.

### REQ-PRESET-003. Предпросмотр

- Статус: `in-progress`
- Приоритет: `must`
- До сохранения оператор ДОЛЖЕН видеть количество вакансий и разбивку по
  ключевым словам, навыкам, компаниям и последним вакансиям.
- Критерии приёмки:
  - предпросмотр считается по тем же правилам, что и сохранённый пресет;
  - пустой результат показывает 0, а не ошибку.

### REQ-PRESET-004. Старый формат

- Статус: `in-progress`
- Приоритет: `must`
- Старые пресеты с `text` и `gate` ДОЛЖНЫ открываться и конвертироваться в
  правила при редактировании, без потери смысла.
- Критерии приёмки:
  - `{"text":"DevOps","gate":"match"}` превращается в два правила;
  - после сохранения пресет работает как раньше.

## KW — ключевые слова

### REQ-KW-001. Фильтр по месту совпадения

- Статус: `done`
- Приоритет: `must`
- Ключевые слова ДОЛЖНЫ фильтроваться по наличию в навыках hh, тексте
  вакансии, заголовке или в тексте+навыках.
- Критерии приёмки:
  - на странице есть выбор места;
  - счётчики пересчитываются по выбранному месту;
  - `text_or_skills` означает «хотя бы одно из двух».

## SRC — источники и обход

### REQ-SRC-001. Почта

- Статус: `in-progress`
- Приоритет: `must`
- Модуль почты ДОЛЖЕН подключать IMAP-ящик по паролю приложения, хранить
  пароль локально в `~/.otbor/mail` с mode `0600`, синхронизировать INBOX и,
  опционально, Sent, и складывать письма в общие диалоги и контакты.
- Критерии приёмки:
  - аккаунт можно добавить, проверить и удалить;
  - повторная синхронизация не создаёт дублей;
  - ошибка одного письма не обрывает проход.

### REQ-SRC-002. Telegram

- Статус: `in-progress`
- Приоритет: `must`
- Модуль Telegram ДОЛЖЕН подключаться по API ID/hash и QR-входу, хранить
  сессию локально в `~/.otbor/telegram` с mode `0600`, синхронизировать
  личные диалоги и сообщения, извлекать контакты и ссылки на вакансии.
- Критерии приёмки:
  - QR-вход не требует SMS-кода;
  - сессия не попадает в БД и логи;
  - повторная синхронизация идемпотентна.

### REQ-SRC-003. Расписания источников

- Статус: `in-progress`
- Приоритет: `must`
- Одно расписание ДОЛЖНО уметь запускать не только поиск hh, но и
  синхронизацию почты, Telegram, гидратацию вакансий и компаний.
- Критерии приёмки:
  - у расписания есть вид, цель и опции;
  - worker диспетчеризует по виду;
  - ошибка одного расписания не останавливает остальные.

### REQ-SRC-004. Гидратация вакансий

- Статус: `in-progress`
- Приоритет: `must`
- Расписание ДОЛЖНО добирать полные описания и навыки для вакансий-заглушек
  ограниченными порциями.
- Критерии приёмки:
  - лимит и задержка задаются в опциях;
  - после прохода уменьшается число заглушек;
  - ошибки видны в `last_error`.

### REQ-SRC-005. Гидратация компаний

- Статус: `in-progress`
- Приоритет: `should`
- Расписание ДОЛЖНО обновлять профили компаний ограниченными порциями:
  рейтинг, сайт, логотип, отрасли.
- Критерии приёмки:
  - лимит задаётся в опциях;
  - неразбираемая страница пишет `last_error`, но не роняет worker.

## CONTACT — контакты

### REQ-CONTACT-001. Источники

- Статус: `in-progress`
- Приоритет: `must`
- Контакты ДОЛЖНЫ собираться из описаний вакансий hh, почты, Telegram и
  чатов hh. Типы: email, телефон, Telegram, чат hh, другое.
- Критерии приёмки:
  - каждый контакт хранит источник и доказательство;
  - дубли по типу и значению не создаются;
  - контакт можно связать с вакансией и компанией.

### REQ-CONTACT-002. Страница контактов

- Статус: `proposed`
- Приоритет: `must`
- ДОЛЖНА быть страница со списком контактов, фильтрами по источнику и типу,
  поиском и переходом к вакансии/диалогу.
- Критерии приёмки:
  - видны имя, роль, контакт, источник и последнее подтверждение;
  - контакт можно удалить;
  - список не показывает тестовые записи.

### REQ-CONTACT-003. Секция в вакансии

- Статус: `proposed`
- Приоритет: `should`
- На странице вакансии ДОЛЖНА быть секция контактов, найденных в её тексте.
- Критерии приёмки:
  - email и Telegram кликабельны;
  - видно, откуда взят контакт;
  - секция не дублирует общий список.

## UI — интерфейс

### REQ-UI-001. Нумерация строк

- Статус: `done`
- Приоритет: `should`
- Все таблицы ДОЛЖНЫ нумеровать строки. При пагинации нумерация продолжается.
- Критерии приёмки:
  - колонка «№» есть в каждой таблице;
  - на второй странице номера продолжаются.

### REQ-UI-002. Хлебные крошки

- Статус: `done`
- Приоритет: `should`
- Детальные страницы ДОЛЖНЫ использовать компонент `Breadcrumb` из
  shadcn-vue, а не самодельную ссылку «Назад».
- Критерии приёмки:
  - в крошках есть родительский раздел и текущая страница;
  - компонент один для всех детальных страниц.

### REQ-UI-003. Понятные названия

- Статус: `done`
- Приоритет: `should`
- Внутренний термин «гейт» в интерфейсе ДОЛЖЕН называться «Проверка
  заголовка» и сопровождаться коротким объяснением.
- Критерии приёмки:
  - на странице вакансий нет слова «гейт» без пояснения;
  - фильтр называется «Проверка заголовка».

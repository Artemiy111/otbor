# Требования otbor

Статус: живой документ. Дата: 02.11.2026.

## Как читать

- **Запрос** — формулировка пользователя. Я только причёсываю язык, не
  добавляю смысл.
- **Происхождение: user** — это было в запросе.
- **Происхождение: derived** — это моё предположение, как запрос превратить
  в проверяемое требование. Такое нельзя считать согласованным, пока
  пользователь не подтвердит.
- **Критерии приёмки** — тоже предложение, а не факт. Для `derived` они
  особенно требуют подтверждения.
- ID: `REQ-<область>-<номер>`.
- Статус: `proposed` → `accepted` → `in-progress` → `done` | `dropped`.
- Приоритет: `must`, `should`, `may`.
- «ДОЛЖЕН / СЛЕДУЕТ / МОЖЕТ» — в смысле RFC 2119.

## BL — чёрный список

### Запрос

> Хочу ещё чёрный список компаний на нескольких уровнях. Список на аккаунт в
> моём приложении — действует на все аккаунты hh. Список на конкретный
> аккаунт hh — дополняет общий список. Также у аккаунта на hh есть свой
> механизм скрытия вакансий или работодателей — он тоже должен работать как
> дополнительный механизм.

### REQ-BL-001. Общий список приложения

- Происхождение: `user`
- Статус: `proposed`
- Приоритет: `must`
- Есть чёрный список на уровне приложения. Он действует на все hh-аккаунты.
- Критерии приёмки (предложение): запись видна как «Приложение»; компания из
  списка не показывается и не попадает в отклики ни по одному аккаунту.

### REQ-BL-002. Список конкретного hh-аккаунта

- Происхождение: `user`
- Статус: `proposed`
- Приоритет: `must`
- У каждого hh-аккаунта есть свой дополнительный список. Он дополняет общий
  список приложения, а не заменяет его.
- Критерии приёмки (предложение): запись привязана к аккаунту; блокировка
  действует только для него.

### REQ-BL-003. Штатное скрытие в hh

- Происхождение: `user`
- Статус: `proposed`
- Приоритет: `should`
- Скрытые в кабинете hh вакансии и работодатели работают как ещё один
  дополнительный механизм.
- Критерии приёмки (предложение): записи импортируются, помечены как
  «скрыто в hh» и не дублируют ручные.

### REQ-BL-004. Слои складываются как метки

- Происхождение: `derived`
- Статус: `proposed`
- Приоритет: `must`
- Чёрный список — это метка и фильтр, а не абсолютный запрет. Слои
  складываются: приложение, конкретный hh-аккаунт, штатное скрытие в hh.
- Критерии приёмки (предложение): у компании/вакансии видно, какие слои
  сработали; фильтр может как исключить их, так и показать.

### REQ-BL-008. Показ и автоотклики

- Происхождение: `user`
- Статус: `proposed`
- Приоритет: `must`
- Компании из чёрного списка всё равно остаются в поиске и доступны для
  автооткликов, если пресет или фильтр страницы настроен на их показ.
- Критерии приёмки:
  - на странице компаний есть опция «показывать / не показывать»
    заблокированные;
  - на странице компаний есть колонка «Чёрный список»;
  - пресет может явно включить заблокированные компании;
  - если пресет их включает, автоотклик по ним не блокируется только из-за
    чёрного списка.

### REQ-BL-005. Компания или вакансия

- Происхождение: `derived`
- Статус: `proposed`
- Приоритет: `must`
- Блокировать можно компанию или конкретную вакансию. Блокировка компании
  скрывает все её вакансии, включая новые.
- Критерии приёмки (предложение): добавить можно по названию, id hh или
  ссылке; новые вакансии компании скрываются сами.

### REQ-BL-006. Корпус не удаляется

- Происхождение: `derived`
- Статус: `proposed`
- Приоритет: `must`
- Блокировка — фильтр видимости и решений, а не удаление из корпуса.
- Критерии приёмки (предложение): строка остаётся в БД; после снятия
  блокировки вакансия снова видна без повторного обхода.

### REQ-BL-007. Управление и аудит

- Происхождение: `derived`
- Статус: `proposed`
- Приоритет: `should`
- В UI есть вкладки «Приложение», «Аккаунт hh», «Скрыто в hh», поиск,
  добавление и удаление. У записи есть источник, причина, автор и время.
- Критерии приёмки (предложение): импортированные записи не путаются с
  ручными; удаление ручной записи не трогает импортированные.

## PRESET — пресеты

### Запрос

> Нафиг мне делать только проверку заголовка, мне нужно, чтобы это было лишь
> частным случаем в пресете, а пресет почти по всем параметрам должен
> фильтровать.
>
> Пресеты я вообще не понял: почему настолько примитивные стили по сравнению
> со старым проектом?
>
> Что такое гейт — я тоже не понял.

### REQ-PRESET-001. Пресет фильтрует почти по всем параметрам

- Происхождение: `user`
- Статус: `in-progress`
- Приоритет: `must`
- Пресет — набор условий по параметрам вакансии, а не форма на три поля.
- Критерии приёмки (предложение): условия складываются; в UI можно добавить
  и удалить условие; сохранённый пресет даёт то же число вакансий, что и
  предпросмотр.

### REQ-PRESET-002. Гейт — частный случай

- Происхождение: `user`
- Статус: `in-progress`
- Приоритет: `must`
- Проверка заголовка — одно из условий пресета, а не отдельная обязательная
  сущность.
- Критерии приёмки (предложение): условие `gate = match|unknown|reject`
  сочетается с любыми другими; без него пресет не фильтрует по вердикту.

### REQ-PRESET-003. Понятный гейт

- Происхождение: `user`
- Статус: `done`
- Приоритет: `should`
- В интерфейсе «гейт» называется «Проверка заголовка» и объясняется.
- Критерии приёмки (предложение): на странице вакансий есть короткое
  объяснение, что это правило по заголовку, а не ИИ.

### REQ-PRESET-004. Уровень старого проекта

- Происхождение: `user`
- Статус: `in-progress`
- Приоритет: `should`
- Экран пресетов должен быть не примитивнее старого проекта: список,
  детали, правила, предпросмотр.
- Критерии приёмки (предложение): мастер-детальный экран; правила
  «поле / оператор / значение»; разбивка по ключевым словам, навыкам,
  компаниям и вакансиям.

### REQ-PRESET-005. Список полей и операторов

- Происхождение: `derived`
- Статус: `in-progress`
- Приоритет: `must`
- Поля: заголовок, описание, навыки, ключевые слова, работодатель, город,
  зарплата, валюта, грейд, формат работы, опыт, занятость, свежесть, архив,
  вердикт заголовка, роль, источник, отзывы, длина описания, число навыков.
- Операторы: `contains`, `not_contains`, `eq`, `neq`, `in`, `not_in`, `gte`,
  `lte`, `is_true`, `is_false`.
- Критерии приёмки (предложение): операторы ограничены типом поля.

### REQ-PRESET-006. Старый формат

- Происхождение: `derived`
- Статус: `in-progress`
- Приоритет: `must`
- Старые пресеты с `text` и `gate` открываются и конвертируются в условия.
- Критерии приёмки (предложение):
  `{"text":"DevOps","gate":"match"}` превращается в два условия.

---

### REQ-PRESET-007. Чёрный список в пресете

- Происхождение: `derived`
- Статус: `proposed`
- Приоритет: `must`
- Пресет может явно включать или исключать компании из чёрного списка.
  По умолчанию пресет исключает заблокированные, пока правило не говорит
  обратное.
- Критерии приёмки (предложение): в конструкторе есть условие по чёрному
  списку; предпросмотр показывает, сколько заблокированных попало в срез.

## KW — ключевые слова

### Запрос

> Ключевые слова ещё фильтроваться по наличию в навыках HH, или внутри текста
> вакансии, или то + это.

### REQ-KW-001. Место совпадения

- Происхождение: `user`
- Статус: `done`
- Приоритет: `must`
- Ключевые слова фильтруются по наличию в навыках hh, тексте вакансии,
  заголовке или в тексте + навыках.
- Критерии приёмки (предложение): на странице есть выбор места; счётчики
  пересчитываются; «текст + навыки» значит хотя бы одно из двух.

## SRC — источники и обход

### Запрос

> Обход вообще странно сейчас сделан. У меня вообще-то должны появиться
> модули с почтой и телеграмом, и у них тоже обход по расписанию. Ещё обход
> или очереди для гидратации вакансий, компаний. Вот эти модули тоже добавь.
> Плюс добавь секцию контактов из hh + tg.

### REQ-SRC-001. Почта

- Происхождение: `user`
- Статус: `in-progress`
- Приоритет: `must`
- Есть модуль почты и обход почты по расписанию.
- Критерии приёмки (предложение): IMAP-аккаунт можно добавить, проверить и
  удалить; синхронизация идёт по расписанию и вручную; письма не дублируются.

### REQ-SRC-002. Telegram

- Происхождение: `user`
- Статус: `in-progress`
- Приоритет: `must`
- Есть модуль Telegram и обход Telegram по расписанию.
- Критерии приёмки (предложение): подключение по API ID/hash и QR; сессия
  хранится локально; синхронизация личных диалогов идемпотентна.

### REQ-SRC-003. Расписания источников

- Происхождение: `user`
- Статус: `in-progress`
- Приоритет: `must`
- Обход — это не только поиск hh. Расписание умеет запускать почту,
  Telegram, гидратацию вакансий и компаний.
- Критерии приёмки (предложение): у расписания есть вид, цель и опции;
  worker диспетчеризует по виду; ошибка одного не роняет остальные.

### REQ-SRC-004. Гидратация вакансий

- Происхождение: `user`
- Статус: `in-progress`
- Приоритет: `must`
- Есть обход или очередь для гидратации вакансий.
- Критерии приёмки (предложение): ограниченные порции; лимит и задержка в
  опциях; ошибки видны в `last_error`.

### REQ-SRC-005. Гидратация компаний

- Происхождение: `user`
- Статус: `in-progress`
- Приоритет: `should`
- Есть обход или очередь для гидратации компаний.
- Критерии приёмки (предложение): ограниченные порции; обновляются рейтинг,
  сайт, логотип, отрасли; неразбираемая страница не роняет worker.

### REQ-SRC-006. Контакты из hh и Telegram

- Происхождение: `user`
- Статус: `in-progress`
- Приоритет: `must`
- Есть секция контактов из hh и Telegram.
- Критерии приёмки (предложение): контакты из вакансий, почты, Telegram и
  чатов hh; источник и доказательство у каждой записи; дублей нет.

## CONTACT — контакты

### REQ-CONTACT-001. Источники

- Происхождение: `user`
- Статус: `in-progress`
- Приоритет: `must`
- Контакты собираются из описаний вакансий hh, почты, Telegram и чатов hh.
- Критерии приёмки (предложение): email, телефон, Telegram, чат hh; связь с

### REQ-CONTACT-002. Страница контактов

- Происхождение: `derived`
- Статус: `proposed`
- Приоритет: `must`
- Есть страница со списком контактов, фильтрами по источнику и типу, поиском.
- Критерии приёмки (предложение): видны имя, роль, контакт, источник;

### REQ-CONTACT-003. Секция в вакансии

- Происхождение: `derived`
- Статус: `proposed`
- Приоритет: `should`

- Критерии приёмки (предложение): email и Telegram кликабельны; видно
  источник; секция не дублирует общий список.

## Открытые вопросы

Это не требования, а места, где нужно решение пользователя:

1. Чёрный список: блокировать только компании или ещё отдельные вакансии?
   В запросе есть и «компании», и «скрытие вакансий или работодателей».
2. Чёрный список: что важнее при конфликте — общий список приложения или
   ручное исключение для конкретного hh-аккаунта?
3. Контакты из чатов hh: нужен ли отдельный browser-harness или достаточно
   импорта из почты и Telegram на первом этапе?

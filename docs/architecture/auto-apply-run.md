# otbor: автоотбор и автоотправка откликов

Статус: принято к реализации. Дата: 05.11.2026. Продолжение
[apply-filter.md](./apply-filter.md).

## Что нужно

Оператор сам задаёт фильтр и все параметры отбора, а автоматическую подачу
откликов включает и выключает сам. По умолчанию всё выключено.

## Параметры (хранятся рядом с фильтром, в `apply_filter`)

| Параметр | Значения | По умолчанию |
|---|---|---|
| `auto_mode` | `off` / `drafts` / `auto` | `off` |
| `daily_limit` | откликов в сутки на hh-аккаунт | **200** (лимит hh) |
| `batch_size` | сколько вакансий брать за один запуск | 20 |
| `sort` | `priority` / `fit` / `newest` / `salary` | `priority` |
| `sort_direction` | `desc` (лучшие первыми) / `asc` (весь порядок инвертирован, худшие первыми; `nulls last` остаётся в конце). Влияет только на выбор исполнителя, решения не устаревают | `desc` |
| `writing_harness` / `writing_model` / `writing_effort` | агент, модель и effort, которые пишут письма автоотбора (попадают в payload inference-задачи). `null` = умолчание харнеса; `null`/пустая строка при сохранении очищает, пропуск оставляет. Решения не устаревают | `null` |
| `min_priority` | порог приоритета | 0 |
| `boosts` | список `{ rule: PresetRule, weight: int -50..50 }` | см. ниже |

- `drafts`: создаём отклики, читаем форму, пишем письмо и ответы, оставляем
  черновик. Отправляет оператор.
- `auto`: то же, но готовый кит, прошедший все проверки, отправляется сам.
- `daily_limit` относится к hh-аккаунту, а не к паре аккаунт+резюме. Берётся из
  строки аккаунта (resume = NULL), иначе 200. Переменная
  `OTBOR_DAILY_APPLY_LIMIT` остаётся только как глобальный дефолт вместо 200.
  Считаются отклики `origin = 'otbor'` в состояниях queued/submitting/submitted
  (`preparing` слота ещё не занимает)
  за последние 24 часа (уже есть `recentSubmits` в `ApplicationService`).
- `boosts` заменяют зашитые бонусы детерминированного fit. Каждое правило
  считается тем же SQL, что и фильтр. Fit = 45 + бонусы по словарю (как раньше)
  + сумма весов сработавших boosts, в пределах 0..100. LLM-fit по-прежнему
  перекрывает всё. Дефолт (встроенный, воспроизводит прежние константы):
  `salary >= 250000 (RUB)` +8, `work_format in remote` +5,
  `seniority in middle,senior,lead,unknown` +4. Константы
  `FIT_SALARY_FLOOR` / `FIT_SENIORITY` в `decision.ts` удаляются.
- Приоритет = fit x свежесть. Он живой: `decision.priority` пишется при оценке,
  но все чтения (сортировка, `min_priority`, списки, очередь fit-судьи) считают
  `round(fit x свежесть, 2)` в SQL на момент запроса (`livePriorityExpr` в
  `DecisionRepository`). Период полураспада берётся из `apply_filter` пары
  (аккаунт, резюме), иначе из строки аккаунта, иначе 72 ч. Решение не
  устаревает из-за возраста вакансии; не-`apply` решения сохраняют 0.

## Исполнитель `AutoApplyRunner`

Новый вид расписания `apply` (как `evaluate`/`fit`): работает по расписанию и
по `ScheduleRunNow`. Для каждого hh-аккаунта пользователя и каждой строки
`apply_filter` с `auto_mode != off`:

1. **Бюджет.** `remaining = daily_limit - recentSubmits(account)`. Если <= 0,
   ничего не берём.
2. **Выбор.** Берём текущие (не устаревшие) решения `verdict = apply` этого
   аккаунта и резюме, по которым ещё нет отклика (account, vacancy, resume),
   с `priority >= min_priority`, в порядке `sort` и `sort_direction`, не больше
   `min(batch_size, remaining)`.
3. **Создание.** `createFromDecision` в режиме `auto` или `drafts` по
   `auto_mode`. Он ставит чтение формы (`form_read`).
4. **Письмо.** Для откликов с готовой, свежей формой и без кита исполнитель
   ставит inference-задачу письма (`WritingService.coverLetter`) и, если у формы
   есть вопросы без детерминированных ответов, задачу ответов
   (`WritingService.answers`). Идемпотентность: не больше одной задачи письма на
   (отклик, formHash).
5. **Кит.** Когда задача завершена, результат разбирается и сохраняется через
   `setKit` с опцией `runner: true` (её передаёт только раннер; сохранение кита
   оператором через RPC никогда не отправляет). Для `auto` отклик в состоянии
   `preparing` проходит общий шлюз `trySubmit`: если кит прошёл `checkKit`,
   шлюз занимает слот и переводит отклик в `queued`. Если кит не проходит
   проверки, формой нужен человек, подсказка с `blockers`,
   отклик переходит в `needs_human` с кодом и понятной причиной и не отправляется.
6. **Отправка** остаётся как есть: намерение пишется до клика, неоднозначность
   идёт в reconcile, повторной отправки нет.

### Режим строки и уже созданные заявки

Заявку двигает только раннер, и только пока режим строки, которая ведёт её
(пара «аккаунт, резюме» или строка аккаунта), это позволяет:

- `auto`-заявка идёт, только пока строка `auto` (дальше возможна отправка);
- `drafts`-заявка готовится (форма, письмо, кит; отправки никогда) пока строка
  `drafts` **или** `auto`: после переключения аккаунта с `drafts` на `auto`
  черновики без кита не зависают;
- `off` останавливает всё. В прогрессе такая заявка показывается как
  «Режим автоотклика выключен — не обрабатывается».

Правило одно на оба места: `runnerMayAdvance` в `services/autoRunMode.ts`.

### Продвижение сразу после задачи

Каждый шаг не ждёт тика расписания. Когда завершается `form_read`, а также
inference-задача письма (ключ `autoapply:writing:<отклик>:...`; любой
терминальный статус, кроме повтора), `QueueService.complete` отдаёт id
автооткликов, ради которых задача шла, и **после коммита** транзакции
завершения вызывает `AutoApplyRunner.advance(userId, ids)` отдельным fiber
(`Effect.forkDetach`): ответ харнессу не ждёт раннера, сбой попадает только в
`Effect.logWarning`. `advance` выполняет тот же шаг, что и проход (проверка
режима строки, `retry_at`, идемпотентные ключи), но заявок не создаёт.
Расписание остаётся запасным путём. В тестах продвижение выключается опцией
`advanceOnComplete: false` у `QueueService`, чтобы счётчики проходов были
детерминированы.

## Состояния автоотклика и причины остановки

`preparing` - автоотклик (`auto_run = 'auto'`), у которого ещё нет слота: он
ждёт форму, письмо, кит, свободный дневной слот или время повтора.
`queued` означает только «слот занят (`intent_at`), submit поставлен в очередь».
`preparing` заводит только раннер (`createFromDecision` с `autoRun`); любая другая
заявка (CLI, MCP, веб, вручную) создаётся `draft`, у неё нет `auto_run`, и
автоматически она не отправляется никогда: автоотправка - режим `auto` строки
apply filter. Шлюз `trySubmit` (триггер `auto`) переводит
`preparing -> queued`, записывая `intent_at`. `drafts`-отклики живут в `draft`.

```
auto:  (создан) preparing --шлюз--> queued --lease--> submitting --> submitted
                  |  ^                                    \--> needs_human / failed / reconcile
                  |  +-- retry_at наступил: раннер возобновляет
                  +--> needs_human (постоянная причина или повторы кончились)
                  +--> draft (режим auto выключили)
                  +--> skipped (оператор)
```

Рядом с состоянием у заявки три поля: `blocked_reason` (код из замкнутого
набора, check в миграции 0046), `retry_at` (когда раннер возобновит ожидающий
`preparing`) и `auto_retries` (потраченные автоповторы). `last_error` остаётся
текстом для человека. Переход `ApplicationRepository.transition` сам ведёт
код: без явного `blockedReason` переход в `needs_human`/`failed` ставит
`operator`, любой другой (approve, retry, claim, skip) снимает код и `retry_at`.

| Код | Смысл | Что происходит с автооткликом |
|---|---|---|
| `captcha` | hh попросил капчу, отправки аккаунта на паузе, пауза снимается сама | `preparing` без `retry_at`; после снятия паузы (автоматически или `HhAccountSubmitResume`) раннер отправляет снова |
| `no_resume` | нет резюме для откликов | `needs_human` |
| `form_unreadable` | раскладка формы не распознана, пришла форма другой вакансии | `needs_human` |
| `form_gone` | вакансия больше не принимает отклики | `needs_human` (архив вакансии: `skipped`) |
| `form_read_failed` | форму не удалось прочитать | `preparing` с повтором, после 3 повторов `needs_human` |
| `form_hint_blocked` | подсказка ответа заблокирована | `needs_human` |
| `kit_refused` | кит не прошёл `checkKit` | `needs_human` |
| `writing_failed` | задача письма умерла (харнес офлайн, квота) | `preparing` с повтором, после 3 повторов `needs_human` |
| `daily_cap` | дневной лимит аккаунта | остаётся `preparing`, `retry_at` = момент, когда освободится первый слот (`resetsAt` шлюза) |
| `submit_not_sent` | submit заведомо не отправил отклик | `needs_human` / `failed` (трогает уже `submitting`) |
| `reconcile_unclear` | сверка не установила, ушёл ли отклик | `needs_human` |
| `operator` | прочее или ручное решение | `needs_human` |

Автоповторы (`form_read_failed`, `writing_failed`): заявка остаётся `preparing`,
получает `retry_at` через 1 ч, 4 ч, 12 ч и `auto_retries + 1`; на четвёртом
сбое она уходит в `needs_human` с тем же кодом. Раннер берёт `preparing`-заявки
только с `retry_at is null or retry_at <= now()`; срок перепроверяется в снимке
заявки, а `blocked_reason`/`retry_at` снимаются условно (`retry_at` вышел), так
что соседний проход не перепрыгнет ожидание. Дойдя до заявки, он снимает
`blocked_reason`/`retry_at` и повторяет шаг: для письма освобождает ключ мёртвой
задачи (`<key>:retried:<n>`, как делает ручной повтор) и ставит новую, для чтения
формы ставит принудительное чтение. Для `daily_cap` раннер просто ещё раз
проходит шлюз. `drafts`-отклики повторов не получают: они сразу `needs_human`.
`retry`/`approve` оператора сбрасывают код, `retry_at` и `auto_retries`. Бюджет
повторов - на препятствие, а не на жизнь заявки: он обнуляется, когда шаг удался
(сохранён кит, чтение формы прошло для заявки с `form_read_failed`). Сбой чтения
формы откладывает только заявки, которые ещё не ждут: `daily_cap` и ожидание с
будущим `retry_at` не затираются.

Режим строки apply filter и `preparing`: после любой записи строки (`set`,
`fromPreset`) вызывается `demoteUngovernedAuto`, он возвращает в `draft`
`preparing`-автозаявки, которыми строка больше не управляет в `auto`.
`pendingAutoSlots` дополнительно считает только заявки с управляющей строкой
`auto`, поэтому осиротевшие не резервируют слоты.

Отказ операции (`ApplicationService`: approve, retry, skip, setKit, create...)
откатывает транзакцию: ничего из записанного до отказа не остаётся.

В ходе автоотбора (веб, вкладка «Ход») ожидающая заявка видна как этап
«Ждёт повтора» с русским смыслом кода и временем возобновления
(`AutoApplyProgressItem.blockedReason` / `retryAt`, счётчик `summary.blocked`).

Сходимость: исполнитель идемпотентен и опрашивает состояние, а не держит его в
памяти. Любой запуск может подхватить недоделанные отклики предыдущего.

## Безопасность

- `auto_mode` по умолчанию `off`; включает только оператор.
- Отправка возможна только при `auto`, лимит суток соблюдается транзакционно в
  `approve`/`setKit` (уже есть проверка `recent.used >= dailyApplyLimit`).
- Харнес не доверенный: исполнитель не принимает от него ничего, кроме текста
  письма и ответов, и проверяет их `checkKit` (стиль, длина, обязательные
  вопросы).
- Письмо пишется по существующим промптам (без выдуманного опыта).

## Параллельность браузерных задач

Один аккаунт - один харнесс (аренда `account_lease`: Chrome блокирует профиль),
но не одна задача. `QueueRepository.claim` отдаёт харнессу-арендатору до
«браузерных задач на аккаунт» (по умолчанию 4) задач аккаунта разом, из них не
больше «отправок на аккаунт» (по умолчанию 1) действующих (`submit`,
`letter_attach`). Остальные стадии (`form_read`, `reconcile`, `chat_read`,
`negotiations_sync`, `resume_sync`) только читают. At-most-once это не
затрагивает: он на уровне заявки (одна попытка отправки, намерение до клика,
ключи идемпотентности).

Выбор кандидата сам отбрасывает то, что взять нельзя (аккаунт у другого
держателя, потолок аккаунта), поэтому занятый аккаунт не блокирует inference и
другие аккаунты. Гонку двух claim одного аккаунта закрывает блокировка строки
`account_lease` (upsert): второй ждёт коммита первого и пересчитывает занятость;
проигравший пробует следующего кандидата.

### Настройки живут в базе

Числа выше, темп, часовой лимит и потоки харнесса - не переменные окружения, а
строка `user_settings` (одна на пользователя, RLS как у соседних таблиц). Их
правят на странице «Настройки», блок «Отклики и браузер» (RPC `SettingsGet` /
`SettingsUpdate`, CLI `otbor settings get|set`). `claim` читает строку владельца
задачи при каждой выдаче (в самом запросе выбора и ещё раз под блокировкой
аккаунта), так что правка действует сразу, перезапуск не нужен.

| Поле | По умолчанию | Диапазон |
|---|---|---|
| браузерных задач на аккаунт | 4 | 1..12 |
| отправок (действующих) на аккаунт | 1 | 1..12, не больше браузерных |
| пауза между отправками, с | 75 | 0..3600 |
| случайная добавка к паузе, % | 50 | 0..200 |
| не больше отправок в час на аккаунт | нет | 1..1000 или пусто |
| потоки харнесса | 6 | 1..12 |

Переменные `OTBOR_ACCOUNT_BROWSER_CONCURRENCY`, `OTBOR_ACCOUNT_SUBMIT_CONCURRENCY`,
`OTBOR_ACCOUNT_SUBMIT_INTERVAL_SECONDS`, `OTBOR_ACCOUNT_SUBMIT_JITTER_PERCENT` и
`OTBOR_HARNESS_CONCURRENCY` остались только начальными значениями: они
действуют, пока у пользователя нет строки. Настройки глобальные для
пользователя; переопределений по аккаунту нет.

**Потоки харнесса.** Ответ `HarnessLeaseNext` несёт `harnessSlots` из настроек.
Харнесс запускает 12 циклов выдачи (максимум), а работают из них первые
`harnessSlots`: остальные простаивают (раз в секунду проверяют число) и
просыпаются, когда оно вырастет; уменьшение вступает в силу, когда цикл
доделает начатую задачу. Нет поля в ответе - остаётся значение
`OTBOR_HARNESS_CONCURRENCY` / `--concurrency`. Потолок действующих задач профиля
внутри харнесса (`accountActingConcurrency` в `playwright.ts`) по умолчанию
поднят до 12: облако - единственный хозяин потолка, а фиксированное число,
выбранное при старте, не давало бы настройкам действовать без перезапуска.
`OTBOR_HARNESS_ACCOUNT_SUBMIT_CONCURRENCY` остаётся явной страховкой.

### Темп отправок, часовой лимит и блокировка после капчи

hh отвечает капчей на POST отклика, когда их идёт слишком много подряд (форма
при этом открывается без капчи). Пока человек не решил капчу в профиле браузера,
hh показывает её на каждом отклике; после решения отклики идут, пока hh не
сработает снова. Поэтому фиксированная пауза не годилась: она давала новую
капчу каждые 5 минут. Теперь капча ставит паузу с нарастающим сроком, и она снимается сама.

- **Темп.** `claim` не выдаёт `submit` и `letter_attach` аккаунта, пока не
  вышел `hh_account.submit_next_at`. Выдав такую задачу, `claim` сам ставит
  `submit_next_at = now() + пауза` плюс случайная добавка (настройки). Это
  делается под блокировкой `account_lease` вместе с проверкой потолков, поэтому
  параллельные claim не выдают две задачи в одно окно. Читающие стадии темпом
  не ограничены. 0 выключает темп.
- **Часовой лимит.** Если задан, `claim` не выдаёт `submit` аккаунта, когда за
  последний скользящий час уже выдано столько `submit` (считается по
  `harness_jobs.leased_at`; письма и чтения не считаются). Проверка в запросе
  выбора и ещё раз под блокировкой аккаунта. Лимит задают, когда по эпизодам
  капчи (ниже) станет известен порог hh.
- **Блокировка после капчи.** Если задача аккаунта завершилась с `captcha`
  (`QueueService.complete`), в `hh_account` пишутся `submit_blocked_at = now()` и
  `submit_block_reason = 'captcha'` и `submit_retry_at` (5 минут, при капчах подряд без откликов удваивается до часа). Пока блокировка стоит, `claim` не
  выдаёт действующие задачи аккаунта; чтения идут. Повторная капча при уже
  стоящей блокировке ничего не меняет. Её снимает worker (`captchaAutoResume`, всегда, раз в минуту) по `submit_retry_at`; оператор может раньше: RPC
  `HhAccountSubmitResume({ hhAccountId })`, команда `otbor hh resume [аккаунт]`
  или кнопка «Продолжить» (карточка «Параллельность» на странице очереди и
  страница «Аккаунты hh.ru» показывают предупреждение). Капчу решают в профиле
  харнеса: `otbor hh login --profile <профиль аккаунта>` открывает его в окне
  браузера. Возобновление ставит `submit_resumed_at`, закрывает открытый эпизод и
  возвращает раннеру автозаявки, ждавшие капчу (раннер двигает их сразу).
- **Автозаявка после капчи.** submit, на который hh ответил капчей после клика,
  идёт в сверку как любой неоднозначный. Если сверка доказала, что отклика нет
  (`unsent`), автозаявка (`auto_run = 'auto'`, управляющая строка фильтра всё ещё
  в `auto`) переходит не в `draft`, а в `preparing` с `blocked_reason = 'captcha'`
  и без `retry_at`; счётчик автоповторов не растёт. Раннер такие заявки не берёт,
  пока блокировка стоит; после «Продолжить» код снимается, раннер и шлюз
  `trySubmit` ставят новый submit (прежний закрыт сверкой как `clicked: false`,
  так что at-most-once сохраняется). Пока блокировка стоит, шлюз автозаявку в
  очередь не ставит, а оставляет `preparing/captcha`. Если `unsent` без
  блокировки, автозаявка получает обычный автоповтор с `submit_not_sent` (1 ч,
  4 ч, 12 ч, затем `draft`). Ручные заявки по-прежнему возвращаются в `draft`
  («одобрить заново»); их одобрение при блокировке ставит submit, и он ждёт в
  очереди.
- **Эпизоды капчи.** Когда капча ставит блокировку, в `hh_captcha_episode`
  открывается строка: `captcha_at`, число подтверждённых откликов otbor
  (`submitted`, без импортированных) между прошлым возобновлением (или за всё
  время) и капчей, время первого и последнего из них. Возобновление проставляет
  `resumed_at`. `HhCaptchaEpisodesList`, `otbor hh captcha` и карточка «Капча
  hh.ru» на странице аккаунтов показывают «капча после N откликов за M мин».
- **Видимость.** Вид параллельности (`QueueConcurrencyGet`) показывает действующие
  настройки, по аккаунту блокировку (`submitBlockedAt`) и время, раньше которого
  следующая отправка не уйдёт; `HhAccountRecord` несёт `submitBlockedAt`.

## Интерфейс

- Страница `/apply-filter`: переключатель режима, лимит, партия, сортировка,
  порог, редактор boosts, кнопка «Запустить сейчас», счётчик «сегодня
  отправлено X из N».
- CLI: `otbor filter set --auto off|drafts|auto --daily-limit N --batch N
  --sort priority|fit|newest|salary --order desc|asc --min-priority N`, `otbor apply run`
  (запуск расписания сейчас).
- MCP: чтение параметров; включение режима `auto` через MCP НЕ даётся
  (только `off`/`drafts`), отправку включает человек из UI/CLI.

## Этапы

1. Параметры, boosts, лимит 200 (контракт, домен, cloud, миграция).
2. `AutoApplyRunner` и расписание `apply`.
3. UI, CLI, MCP.

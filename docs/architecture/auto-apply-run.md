# otbor: автоотбор и автоотправка откликов

Статус: принято к реализации. Дата: 05.11.2026. Продолжение
[apply-filter.md](./apply-filter.md).

## Что нужно

Оператор сам задаёт фильтр и все параметры отбора, а автоматическую подачу
откликов включает и выключает сам. По умолчанию всё выключено.

## Параметры (хранятся рядом с фильтром, в `apply_filter`)

| Параметр | Значения | По умолчанию |
|---|---|---|
| `auto_mode` | `off` / `drafts` / `auto` | `off` |
| `daily_limit` | откликов в сутки на hh-аккаунт | **200** (лимит hh) |
| `batch_size` | сколько вакансий брать за один запуск | 20 |
| `sort` | `priority` / `fit` / `newest` / `salary` | `priority` |
| `min_priority` | порог приоритета | 0 |
| `boosts` | список `{ rule: PresetRule, weight: int -50..50 }` | см. ниже |

- `drafts`: создаём отклики, читаем форму, пишем письмо и ответы, оставляем
  черновик. Отправляет оператор.
- `auto`: то же, но готовый кит, прошедший все проверки, отправляется сам.
- `daily_limit` относится к hh-аккаунту, а не к паре аккаунт+резюме. Берётся из
  строки аккаунта (resume = NULL), иначе 200. Переменная
  `OTBOR_DAILY_APPLY_LIMIT` остаётся только как глобальный дефолт вместо 200.
  Считаются отклики `origin = 'otbor'` в состояниях queued/submitting/submitted
  за последние 24 часа (уже есть `recentSubmits` в `ApplicationService`).
- `boosts` заменяют зашитые бонусы детерминированного fit. Каждое правило
  считается тем же SQL, что и фильтр. Fit = 45 + бонусы по словарю (как раньше)
  + сумма весов сработавших boosts, в пределах 0..100. LLM-fit по-прежнему
  перекрывает всё. Дефолт (встроенный, воспроизводит прежние константы):
  `salary >= 250000 (RUB)` +8, `work_format in remote` +5,
  `seniority in middle,senior,lead,unknown` +4. Константы
  `FIT_SALARY_FLOOR` / `FIT_SENIORITY` в `decision.ts` удаляются.
- Приоритет = fit x свежесть, как сейчас.

## Исполнитель `AutoApplyRunner`

Новый вид расписания `apply` (как `evaluate`/`fit`): работает по расписанию и
по `ScheduleRunNow`. Для каждого hh-аккаунта пользователя и каждой строки
`apply_filter` с `auto_mode != off`:

1. **Бюджет.** `remaining = daily_limit - recentSubmits(account)`. Если <= 0,
   ничего не берём.
2. **Выбор.** Берём текущие (не устаревшие) решения `verdict = apply` этого
   аккаунта и резюме, по которым ещё нет отклика (account, vacancy, resume),
   с `priority >= min_priority`, в порядке `sort`, не больше
   `min(batch_size, remaining)`.
3. **Создание.** `createFromDecision` в режиме `auto` или `drafts` по
   `auto_mode`. Он ставит чтение формы (`form_read`).
4. **Письмо.** Для откликов с готовой, свежей формой и без кита исполнитель
   ставит inference-задачу письма (`WritingService.coverLetter`) и, если у формы
   есть вопросы без детерминированных ответов, задачу ответов
   (`WritingService.answers`). Идемпотентность: не больше одной задачи письма на
   (отклик, formHash).
5. **Кит.** Когда задача завершена, результат разбирается и сохраняется через
   `setKit`. Для `auto` отклик в состоянии `queued` отправляется самим `setKit`,
   если кит прошёл `checkKit` (это уже реализовано). Если кит не проходит
   проверки, формой нужен человек, подсказка с `blockers` или вопрос с кодом,
   отклик переходит в `needs_human` с понятной причиной и не отправляется.
6. **Отправка** остаётся как есть: намерение пишется до клика, неоднозначность
   идёт в reconcile, повторной отправки нет.

Сходимость: исполнитель идемпотентен и опрашивает состояние, а не держит его в
памяти. Любой запуск может подхватить недоделанные отклики предыдущего.

## Безопасность

- `auto_mode` по умолчанию `off`; включает только оператор.
- Отправка возможна только при `auto`, лимит суток соблюдается транзакционно в
  `approve`/`setKit` (уже есть проверка `recent.used >= dailyApplyLimit`).
- Харнес не доверенный: исполнитель не принимает от него ничего, кроме текста
  письма и ответов, и проверяет их `checkKit` (стиль, длина, обязательные
  вопросы).
- Письмо пишется по существующим промптам (без выдуманного опыта).

## Интерфейс

- Страница `/apply-filter`: переключатель режима, лимит, партия, сортировка,
  порог, редактор boosts, кнопка «Запустить сейчас», счётчик «сегодня
  отправлено X из N».
- CLI: `otbor filter set --auto off|drafts|auto --daily-limit N --batch N
  --sort priority|fit|newest|salary --min-priority N`, `otbor apply run`
  (запуск расписания сейчас).
- MCP: чтение параметров; включение режима `auto` через MCP НЕ даётся
  (только `off`/`drafts`), отправку включает человек из UI/CLI.

## Этапы

1. Параметры, boosts, лимит 200 (контракт, домен, cloud, миграция).
2. `AutoApplyRunner` и расписание `apply`.
3. UI, CLI, MCP.

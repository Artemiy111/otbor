# otbor: фильтр откликов

Статус: принято к реализации. Дата: 05.11.2026.

## Проблема

Жёсткие условия отбора зашиты в код (`DEFAULT_APPLY_POLICY` в
`packages/domain/src/decision.ts`): порог 250 000 ₽, remote/hybrid, уровни,
режим тестов. `hidden` и `employerCooldown` в `decisionEvaluation.ts` всегда
`false`. Пресеты в решения не подключены. Гейт по заголовку — отдельный слой
(`gate.ts`, `GateService`, таблица `title_verdict`) со своим кэшем.

## Решение

1. **Фильтр откликов** (`apply_filter`) — единственный источник жёстких
   условий. Привязан к паре **hh-аккаунт + резюме**. Это `PresetFilter`
   (правила AND + группы OR), тот же формат, что у пресетов.
2. **Пресет — шаблон.** «Применить пресет к фильтру» копирует его `filter` в
   `apply_filter`. Дальше они независимы; правка пресета фильтр не меняет.
3. **Гейт по заголовку — это правила по `title`.** Стемы бывшей
   `DEVOPS_GATE_POLICY` становятся содержимым системного пресета «DevOps»
   (strong -> группа OR из `title contains`, reject -> `title not_contains`).
   Уровня `unknown` нет: вакансия проходит фильтр или нет. Повышение по
   анализу выражается правилом `analysis_role in (...)` в той же OR-группе.
4. **Правила считаются тем же SQL**, что и поиск (`ruleClause` в
   `LexiconRepository.ts`). Для решения по одной вакансии выполняется один
   запрос, который возвращает булево по каждому правилу и группе. Второго
   вычислителя на TypeScript нет. Из результата строится причина
   `blocked_filter` со списком не прошедших правил.
5. **Вне фильтра остаётся только состояние и скоринг:**
   - `applied` (откликался этим резюме) — блок состояния;
   - архивность — уже добавляется `vacancyFilterSql`, если нет правила `archived`;
   - чёрный список и hidden — правило `hidden` / `includeBlacklisted` фильтра;
   - настройки скоринга хранятся рядом с фильтром в `apply_filter`:
     `min_fit` (по умолчанию 45), `tests` (`allow|human|skip`, по умолчанию
     `human`), `fresh_half_life_hours` (по умолчанию 72).
6. **Откат.** Если для пары (аккаунт, резюме) строки нет, берётся строка
   (аккаунт, резюме = NULL). Если и её нет, берётся встроенный шаблон по
   умолчанию (бывший `DEFAULT_APPLY_POLICY`: salary >= 250000 с `orMissing`,
   `work_format in remote,hybrid`, `seniority in middle,senior,lead,unknown`,
   плюс правила DevOps-гейта). Поведение без настройки не меняется.

## Этапы

**Этап 1 (сейчас).** Контракт, таблица, сервис/RPC, `decide` на фильтре,
системный пресет «DevOps», CLI/MCP/UI редактора фильтра. Таблица
`title_verdict` и колонка `decision.gate` пока остаются: в `decision.gate`
пишется `match`, если фильтр пройден, иначе `unknown`.

**Этап 2 (сделан 05.11.2026, миграция `0036_drop_gate.sql`).** Удалено: `gate.ts`, `GateService`, `title_verdict`, `decision.gate`,
команду `otbor gate`, поля `gate`/`role_family` в правилах пресета и `gate` в
`staleness`.

## Тесты

Интеграционные тесты в `packages/cloud/test/integration` (см. `support.ts`):
фильтр применяется к решению; смена фильтра делает решение устаревшим
(хэш фильтра входит в `inputHash`); откат на строку аккаунта и на встроенный
шаблон; отказ называет не прошедшие правила.
